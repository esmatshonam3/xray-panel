# ربات تلگرام

ربات **داخل خود سرویس وب پنل** و در حالت **webhook** اجرا می‌شود — نه پروسه‌ی
جدا، نه حلقه‌ی polling، و هیچ چیزی برای زنده نگه‌داشتن روی پلتفرم لازم نیست.
آپدیت‌ها به `POST /api/v1/telegram/webhook/{TELEGRAM_WEBHOOK_SECRET}` می‌رسند
و همگام پردازش می‌شوند؛ endpoint همیشه `200` برمی‌گرداند تا تلگرام دوباره
تلاش نکند.

## ۱. راه‌اندازی

ربات **از داخل خود پنل** پیکربندی می‌شود — نیازی به ویرایش متغیر محیطی یا
دیپلوی مجدد نیست. در پنل به صفحه‌ی **ربات تلگرام** بروید:

| فیلد | توضیح |
|---|---|
| **توکن ربات** | از @BotFather. رمزنگاری‌شده ذخیره می‌شود و هرگز در پاسخ API برنمی‌گردد. |
| **نام کاربری ربات** | برای ساخت لینک دعوت زیرمجموعه. اگر خالی بگذارید، هنگام «بررسی توکن» خودکار از تلگرام خوانده می‌شود. |
| **کلید مخفی وبهوک** | با دکمه‌ی ⟳ تولید می‌شود. مسیر وبهوک را غیرقابل‌حدس می‌کند. |
| **شناسه ادمین‌ها** | آیدی عددی ادمین‌ها با کاما. |
| **ربات فعال باشد** | کلید اصلی؛ تا روشن نشود وبهوک پاسخ نمی‌دهد. |
| **ثبت خودکار وبهوک** | در هر بوت پنل، وبهوک دوباره با تلگرام ثبت می‌شود. |

### چهار قدم

1. در **@BotFather** دستور `/newbot` را بزنید و توکن را کپی کنید.
2. توکن را در فیلد «توکن ربات» بچسبانید و **ذخیره** را بزنید.
3. به ربات خود پیام `/id` بدهید — عدد برگشتی را در «شناسه ادمین‌ها» وارد کنید.
   (این دستور را برای همین کار اضافه کردیم تا لازم نباشد آیدی خود را حدس بزنید.)
4. **ثبت وبهوک** را بزنید، سپس **پیام آزمایشی** را امتحان کنید.

> اگر روی لوکال‌هاست تست می‌کنید، تلگرام به HTTPS عمومی نیاز دارد. با
> `ngrok http 8000` یک آدرس بگیرید و `PANEL_BASE_URL` را روی آن بگذارید.

### از کجا مقدار می‌آید؟

ترتیب اولویت: **دیتابیس پنل → متغیر محیطی → مقدار پیش‌فرض**.

در کارت «اتصال ربات» یک برچسب کوچک نشان می‌دهد مقدار مؤثر از کجا آمده است
(`منبع: دیتابیس پنل` یا `منبع: متغیر محیطی`). دکمه‌ی **حذف تنظیمات پنل** همه‌ی
بازنویسی‌های دیتابیس را پاک می‌کند تا متغیرهای محیطی دوباره فعال شوند — برای
بازگشت به حالت اولیه بدون دست‌زدن به دیتابیس.

مقادیر ذخیره‌شده در جدول `settings` نگه داشته می‌شوند:

| کلید | رمزنگاری‌شده؟ |
|---|---|
| `telegram.bot_token` | ✅ Fernet |
| `telegram.webhook_secret` | ✅ Fernet |
| `telegram.bot_username` | ❌ |
| `telegram.admin_ids` | ❌ |
| `telegram.enabled` | ❌ |
| `telegram.auto_set_webhook` | ❌ |

### API معادل (برای اتوماسیون)

| متد | مسیر | کار |
|---|---|---|
| GET | `/api/v1/telegram/config` | خواندن تنظیمات مؤثر (توکن ماسک‌شده) |
| PUT | `/api/v1/telegram/config` | ذخیره‌ی هر زیرمجموعه از فیلدها |
| DELETE | `/api/v1/telegram/config` | حذف بازنویسی‌ها و بازگشت به متغیرهای محیطی |
| POST | `/api/v1/telegram/generate-secret` | تولید کلید مخفی تصادفی |
| POST | `/api/v1/telegram/validate` | بررسی توکن با `getMe` (قبل از ذخیره هم می‌شود: `?token=`) |
| POST | `/api/v1/telegram/test` | ارسال پیام آزمایشی به همه‌ی ادمین‌ها |
| POST | `/api/v1/telegram/setup` | ثبت وبهوک |
| POST | `/api/v1/telegram/unset-webhook` | حذف وبهوک |
| GET | `/api/v1/telegram/status` | هویت ربات، وضعیت وبهوک، تعداد حساب‌های متصل |

```bash
# ذخیره‌ی توکن و آیدی ادمین از خط فرمان
curl -X PUT "$PANEL/api/v1/telegram/config" -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"bot_token":"123456:ABC...","admin_ids":[123456789],"enabled":true}'
```

### اگر ترجیح می‌دهید از متغیر محیطی استفاده کنید

روش قبلی هنوز کامل کار می‌کند و می‌توانید با هم ترکیب کنید (مثلاً توکن در
متغیر محیطی، آیدی ادمین‌ها در پنل):

```env
TELEGRAM_ENABLED=true
TELEGRAM_BOT_TOKEN=123456:ABC-DEF...
TELEGRAM_BOT_USERNAME=my_vpn_bot
TELEGRAM_WEBHOOK_SECRET=<openssl rand -hex 32>
TELEGRAM_ADMIN_IDS=11111111,22222222
TELEGRAM_AUTO_SET_WEBHOOK=true
```

هر مقداری که در پنل ذخیره شود، بر متغیر محیطی مقدم است.

`TELEGRAM_ADMIN_IDS` دسترسی کنسول ادمین را می‌دهد. کاربر پنل با نقش
`support`/`admin`/`owner` که حسابش به تلگرام وصل باشد هم همین دسترسی را دارد.

## ۲. جریان‌های کاربر

| ورودی | نتیجه |
|---|---|
| `/start` | **در اولین تماس** دو دکمه‌ی انتخاب زبان (🇮🇷 / 🇬🇧) نشان می‌دهد؛ پس از انتخاب، حساب پنل ساخته می‌شود و منوی اصلی می‌آید |
| `/start <code>` | همان، به‌علاوه‌ی ثبت کد معرف (لینک دعوت) |
| 👤 حساب من | نام کاربری، شناسه، وضعیت، موجودی، تعداد کانفیگ، مصرف کل، تاریخ عضویت |
| 📦 کانفیگ‌های من | فهرست با آیکن وضعیت؛ انتخاب هر کانفیگ صفحه‌ی جزئیات را باز می‌کند |
| 🔗 دریافت لینک | URI اتصال به‌صورت `<code>` (با یک ضربه کپی می‌شود) |
| 📥 لینک اشتراک | آدرس `sub` و نسخه‌ی `?format=clash` |
| 🖼 تصویر QR | QR واقعی و اسکن‌شدنی به‌صورت عکس |
| ✏️ تغییر نام | نام دلخواه برای کانفیگ (حداکثر ۱۲۰ کاراکتر) |
| 🗑 حذف | با تأیید دو مرحله‌ای (دکمه‌ی بله/خیر) |
| 🛒 خرید سرویس | فهرست پلن → صفحه‌ی پلن → انتخاب روش پرداخت |
| 💳 پرداخت از کیف پول | **فعال‌سازی فوری**؛ اگر موجودی کم باشد این دکمه حتی نمایش داده نمی‌شود |
| 🏦 / 🪙 کارت یا کریپتو | ساخت سفارش + اطلاعات پرداخت → ارسال عکس رسید |
| 🔄 تمدید | انتخاب سرویس → انتخاب پلن → کسر از کیف پول و تمدید فوری |
| 📊 مصرف من | نوار پیشرفت متنی (`▰▰▰▱▱▱▱▱▱▱`) برای هر کانفیگ + جمع کل |
| 💳 کیف پول | موجودی، درآمد زیرمجموعه، ۵ تراکنش آخر با آیکن وضعیت، دکمه‌ی شارژ |
| ➕ شارژ کیف پول | دریافت مبلغ → ساخت سفارش top-up → اطلاعات پرداخت |
| 🎁 زیرمجموعه | کد معرف، لینک `t.me/<bot>?start=<code>`، تعداد دعوت‌شده، درآمد |
| ⚙️ تنظیمات | تغییر زبان + کلید روشن/خاموش سه اعلان (انقضا، حجم، اخبار) |
| 🆘 پشتیبانی | آدرس پشتیبانی + پاسخ سؤال‌های پرتکرار |

### مسیر خرید تا فعال‌سازی

```
/start → 🛒 خرید → انتخاب پلن
   ├── 💳 پرداخت از کیف پول
   │      → کسر فوری + create_order(auto_complete=True) + ساخت سرویس
   └── 🏦 کارت / 🪙 کریپتو
          → create_order()                     وضعیت = pending
          → ربات اطلاعات کارت/کریپتو و کد پیگیری را نشان می‌دهد
          → کاربر عکس رسید را می‌فرستد
          → وضعیت = awaiting_review   و ادمین دکمه‌های تأیید/رد می‌گیرد
          → ادمین ✅ را می‌زند
          → fulfil_payment()
               ├── create_service()  → سرویس روی نود ساخته می‌شود
               ├── پرداخت پورسانت به کیف پول معرف
               └── اطلاع به کاربر در زبان خودش
```

زدن ❌ دلیل را ثبت و به کاربر اطلاع می‌دهد. تأیید دوباره رد می‌شود — handler
ابتدا وضعیت را چک می‌کند، پس دوبار کلیک باعث دو بار ساخت سرویس نمی‌شود
(`test_admin_cannot_approve_twice`).

## ۳. کنسول ادمین

`/admin` (یا دکمه‌ی 🛠 در منو) یک **منوی کاملاً مجزا** باز می‌کند:

| دکمه | محتوا و عملیات |
|---|---|
| 📊 آمار کلی | کاربران، کانفیگ فعال/کل، نودهای آنلاین، پرداخت در انتظار، هشدار فعال، درآمد امروز |
| 👥 کاربران | ۱۰ حساب آخر؛ با انتخاب هر کاربر کارت مدیریتی باز می‌شود |
| کارت کاربر | افزودن موجودی (+۱۰/+۲۵/+۵۰)، تمدید ۳۰ روزه‌ی همه‌ی سرویس‌ها، تغییر وضعیت فعال/غیرفعال |
| 💳 پرداخت‌های در انتظار | تا ۵ سفارش با عکس رسید و دکمه‌های تأیید/رد |
| 🗄 نودها | فهرست نودها با CPU؛ صفحه‌ی هر نود: سلامت زنده (CPU/RAM/Disk/کاربر آنلاین) و همگام‌سازی |
| 📈 گزارش | تعداد کانفیگ به تفکیک وضعیت + مجموع ترافیک |
| 🚨 هشدارها | فهرست هشدارهای فعال؛ با یک ضربه بسته می‌شوند |
| 🏷 پلن‌ها | فهرست پلن‌ها؛ با یک ضربه فعال/غیرفعال می‌شوند |
| 🔎 جستجوی کاربر | جستجو با نام کاربری، ایمیل یا شناسه‌ی عددی |
| 📢 اعلان همگانی | انتخاب مخاطب: **همه کاربران** یا **فقط دارندگان سرویس فعال** |
| 💾 پشتیبان‌گیری | ساخت فوری پشتیبان از داخل تلگرام و نمایش نام فایل و حجم |

ارسال همگانی ترتیبی است و نتیجه‌اش در لاگ حسابرسی با تعداد گیرندگان ثبت
می‌شود. نسخه‌ی «فقط دارندگان سرویس فعال» با یک زیرکوئری روی
`services.status == active` فیلتر می‌کند.

## ۴. اطلاع‌رسانی به کاربر

| محرک | پیام |
|---|---|
| اتمام حجم (`job_sweep`) | «حجم تمام شد — برای ادامه تمدید کنید» + دکمه‌ی تمدید |
| انقضای سرویس | «سرویس منقضی شد — همین حالا فعال کنید» + دکمه‌ی تمدید |
| نزدیک شدن انقضا (`job_expiry_reminders`، پنجره از `notifications.expiry_reminder_days`) | «تا N روز دیگر منقضی می‌شود» |
| تأیید پرداخت | «پرداخت تأیید شد، کانفیگ فعال است» |
| رد پرداخت | «سفارش رد شد، با پشتیبانی تماس بگیرید» |

## ۵. یادداشت‌های طراحی

* **ناوبری بی‌حالت.** همه‌ی صفحه‌ها از `callback_data` قابل دسترسی‌اند
  (`m:*`، `cfg:<id>`، `cfg:<action>:<id>`، `buy:*`، `rn:plan:<plan>:<svc>`،
  `a:*`، `pay:*`)، پس ری‌استارت ربات یا اجرای چند نمونه هیچ تفاوتی برای
  کاربر ایجاد نمی‌کند.
* **دوزبانگی کامل.** هر رشته از `bot/i18n.py` می‌آید. زبان در اولین `/start`
  انتخاب می‌شود و در `BotUser.language` ذخیره می‌گردد؛ منوی دستورات تلگرام هم
  با `language_code` جدا برای fa و en ثبت می‌شود.
* **تنظیمات بدون مهاجرت.** ترجیحات کاربر در `BotUser.state_data["prefs"]`
  نگه داشته می‌شوند، پس افزودن یک کلید جدید نیازی به تغییر اسکیمای دیتابیس ندارد.
* **فقط چند حالت صریح.** `BotUser.state` تنها برای `rename`، `topup`،
  `balance:<id>`، `find` و `broadcast_*` استفاده می‌شود؛ بقیه‌ی ناوبری دکمه‌ای است.
* **بررسی مالکیت.** هر callback مربوط به کانفیگی که به کاربر تعلق ندارد رد
  می‌شود، مگر اینکه فرستنده ادمین باشد (`test_cannot_open_someone_elses_config`).
* **ضد اسپم.** یک سطل توکن برای هر کاربر (`TokenBucket`) انفجار درخواست را پیش
  از رسیدن به دیتابیس حذف می‌کند.
* **همیشه پاسخ به callback.** هر مسیر `answerCallbackQuery` را صدا می‌زند
  وگرنه تلگرام اسپینر را روی دکمه نگه می‌دارد
  (`test_every_callback_is_answered`).
* **بدون فریم‌ورک.** `bot/telegram.py` یک کلاینت httpx روی Bot API است.
  وابستگی کمتر، ورکر polling لازم نیست، و قطعی تلگرام نمی‌تواند سرویس وب را
  قفل کند (همه‌ی تماس‌ها best-effort با لاگ خطا هستند).

## ۶. تست محلی

تلگرام به آدرس HTTPS عمومی نیاز دارد. از تونل استفاده کنید:

```bash
ngrok http 8000
# سپس PANEL_BASE_URL=https://<id>.ngrok-free.app را ست و پنل را ری‌استارت کنید،
# یا فقط بعد از تغییر PANEL_BASE_URL دوباره POST /api/v1/telegram/setup بزنید
```

برای تست بدون تلگرام، مستقیم به وبهوک بزنید — یک endpoint معمولی است:

```bash
curl -X POST "$PANEL/api/v1/telegram/webhook/$TELEGRAM_WEBHOOK_SECRET" \
  -H 'Content-Type: application/json' \
  -d '{"message":{"message_id":1,"chat":{"id":12345},"from":{"id":12345,"username":"tester"},"text":"/start"}}'
```

اگر `TELEGRAM_BOT_TOKEN` خالی باشد، `TelegramClient` به یک no-op با لاگ تبدیل
می‌شود — پس کل جریان بدون دسترسی شبکه هم قابل تست است.
